# Common-base practices audit

- **Repo:** `contact-centre-conversations`
- **Catalog id:** E1 (package `contact_centre_conversations`, env prefix `CONTACT`)
- **Catalogue reference:** [`common-base-practices.md`](https://github.com/portable-genai/.github/blob/main/common-base-practices.md) (checks A1..G7)

This file shipped PRE-FILLED with the verdicts the template can honestly claim on render day, and
the rows below are re-run against THIS tree. It is still not a
substitute for an inspection by somebody other than the author: the repo has not yet entered the
cross-repo practices-audit matrix, and that is recorded as a remaining gap on E1's catalog row.
The rows marked GAP are the work list, in priority order.

**Retrieval, authorisation and policy configuration go beyond the template.** The retrieval and
grounding row (B2) is satisfied: `ports/retrieval.py` is a real governed-RAG boundary and empty
retrieval is a hard "say nothing" rather than an ungrounded answer. Object-level authorisation
(C2) is satisfied: the contact store is tenant-scoped and a cross-tenant read answers 403. The
policy numbers row (B4) is satisfied in an unusual way and worth reading as such: the severity
bands, the disclosure windows, the confidence floors and the allowlists are not module constants
lifted into a frozen dataclass, they are PACKS, validated at boot, and changing one is a data edit
with a schema check rather than a release.

Applicability: a rendered repo ships an `agent/` surface (tool functions plus the A2A card
served at `/.well-known/agent-card.json`), a `ui/` micro-frontend and a full `scripts/` demo
surface, so `[ui]` and `[demo]` checks apply on day one. `infra/terraform/` is the full
stack, so the `[infra]` checks apply too. The agent is scaffolded
and tested but not yet registered with Hrz3; see the R4 row in `COMPLIANCE.md`. A repo with no
user-facing surface should run `make drop-ui` and mark the `[ui]` rows N/A, rather than leaving
a UI half-wired.
**Load-bearing** checks (a FAIL breaks a shared catalog guarantee) are A1-A6, C1-C5, D1-D3 and E1.

(3) After adoption, 10 passed. Three deliberate defects on the fixed tree keep the guard honest: flipping `include_subject_principal` scores 6 failed / 4 passed, clearing `tenant_from_hosted_domain` fails the passthrough guard, and passing a fresh `FederationPolicy()` at the call site instead of the reviewed one scores 4 failed / 6 passed, on the resolved tenant rather than on an attribute. **Two behaviour changes are recorded rather than normalised away.** `assurance` now prefers an `acr` claim where the shipped tail hardcoded `"iap"`; nothing in this repository reads `Principal.assurance` for an authorization decision, so the change is audit-visible only, and IAP assertions do not carry `acr` in practice.
